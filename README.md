# Diff X Hunter

保存 GitHub 仓库与关注点，供后续版本更新调查使用。

## 使用

需要 Python 3.12 或更新版本，以及 uv。在项目根目录运行：

```bash
uv sync
uv run diff-x-hunter add astral-sh/uv "关注依赖解析变化"
uv run diff-x-hunter list
```

`add` 保存一条配置，`list` 显示全部配置。仓库使用 `owner/repo` 格式，一个仓库可以保存多条关注点；重复添加会保存为多条记录。

## 网页配置关注

完成下文 GitHub MCP 配置、确认 Docker 引擎运行后，在项目根目录启动：

```bash
uv run --env-file .env uvicorn diff_x_hunter.web:app --host 127.0.0.1 --port 8000
```

打开 http://127.0.0.1:8000 ，填写 `owner/repo` 格式的仓库和可选关注点，点击“保存并查询”。网页先保存配置，再等待 GitHub MCP 分页读取 Release 列表，排除草稿，从正式版与预发布版中按 `published_at` 选择最新一条，保存资料和关联调用记录，最后返回首页显示成功提示。关注点只作为配置保存，不参与本次 Release 查询。网页和 CLI 使用同一个 SQLite 数据库。

仓库格式错误时不保存、不查询；配置保存失败时不查询，并保留输入。查询或结果保存失败时，已保存配置仍在，页面显示失败提示，数据库可写时记录失败调用。页面不展示原始异常。数据库无法读取时，页面仍显示错误和输入，配置列表提示暂时无法读取。

保存接口校验 `Origin` 与当前请求同源；缺少 `Origin` 时检查 `Referer`。来源不匹配、无效或两者都缺失时返回 403，不保存配置、不调用 MCP。浏览器正常表单无需额外配置；脚本提交需提供同源请求头。

暂无已发布版本时保存配置和成功调用记录，并提示“暂无已发布版本”；访问失败、超时、无效返回及 404 仍按失败处理。

提交会等待查询结束，不自动重试；重复提交新增配置和调用记录，同一 Release 复用已有资料。首页展示“最近一次已保存的查询结论”，URL 参数不能制造成功提示。关闭程序再启动，已保存的配置、版本资料和调用记录仍可读取。

## 查看保存的资料与记录

首页读取 SQLite 数据库，打开或刷新页面不会调用 MCP。

- 版本资料按关注仓库分组，展示已保存的版本标签、正式版／预发布版类型、发布说明原文、原始来源链接及 GitHub 发布时间。同一仓库的多条关注配置不会使版本资料重复展示。这里展示版本资料，尚未生成调查报告。
- 查询记录展示仓库、工具、查询时间（UTC）、成功或失败状态和调用摘要。成功记录通过本地 Release 编号关联版本，点击版本标签可跳到对应资料；同一版本的多次查询分别保留记录。
- 失败记录即使没有关联版本也会展示；新记录说明超时、限流、资料格式无效、不可访问或原因未知，不展示原始异常。暂无资料、暂无发布说明、暂无调用记录和读取失败分别提供提示。

## GitHub MCP 配置

官方镜像为 `ghcr.io/github/github-mcp-server:latest`，需要 Docker 引擎运行。

在项目根目录使用 `.env` 保存本地配置。首次配置时，可复制示例文件：

```bash
cp .env.sample .env
```

已有 `.env` 时直接编辑，避免覆盖已有配置。将 GitHub PAT 填入
`GITHUB_PERSONAL_ACCESS_TOKEN=` 后面；其余配置启用只读模式，并仅提供
`list_releases` 工具。已有配置需将 `GITHUB_TOOLS` 更新为 `list_releases`，然后重启应用使环境变量生效。`.env` 已被 Git 忽略；`.env.sample` 只保留空凭据。

通过 uv 将 `.env` 载入应用进程：

```bash
uv run --env-file .env uvicorn diff_x_hunter.web:app --host 127.0.0.1 --port 8000
```

此命令加载配置并启动网页。`github_mcp.list_releases(owner, repo, page)` 通过
官方 Python MCP SDK 启动 Docker 容器，显式传入上述三个环境变量，调用
`list_releases`（`page` 从 1 开始，`perPage=100`）。
`github_mcp.query_release(owner, repo)` 读取所有分页，排除草稿后按发布时间选择最新
一条；时间相同按 GitHub Release 编号确定稳定顺序，不依据标签名、列表第一条或
GitHub 的 latest 标记。类型直接读取 `prerelease`。

每页实际调用分别记录工具名、页码、每页数量、UTC 时间和结果或错误；最后一页的
摘要记录整个查询选定的版本，并关联本地 Release 编号。中途失败保留已完成页的
记录，不保存未经完整列表确认的“最新版本”。空列表或全部是草稿表示暂无已发布版本。
分页读取用于选择目标，当前每次提交仍仅保存一个版本，不批量保存全部历史。

### 查询失败与状态持久化

所有分页共用默认 60 秒等待期限；到期取消 MCP 等待，记录 `failed/timeout`。
清理连接、保存记录仍需时间，因此整个网页请求不保证严格在 60 秒内结束。
不自动重试。

`query_release()` 返回 `QueryResult`，其中 `outcome` 为本项目定义的业务结论：

| outcome | 含义 |
| --- | --- |
| found | 完整查完，找到已发布版本 |
| empty | 完整查完，没有已发布版本 |
| inaccessible | 有目标访问失败证据，但不确定仓库不存在还是权限/凭据问题 |
| failed | 超时、限流、无效响应或其他未知查询失败 |

仅识别官方 `failed to list releases: GET https://api.github.com/repos/.../releases: ...`
错误格式且目标匹配本次请求的访问错误；403 只有明确权限信息才归不可访问，
限流单独记录。格式不匹配、只有“404”或原因不足时保留 `failed/unknown`。
MCP 版本改变错误格式可能使分类退回 unknown，不会据此猜测仓库不存在。

`tool_calls` 新增 `query_outcome`、`reason_code`、`failure_stage`。
中间成功页不填写整次结论，最后成功页或失败页才填写；失败环节分为 query、parse、save。
调用时间仍是该页调用开始时间，不是整个查询完成时间。
`storage.load_query_results("owner/repo")` 返回该仓库按时间顺序（记录 ID）保存的明确结论；
旧记录和中间成功页不会被当成整次结果。旧字段的 `load_tool_calls()` 接口保持不变。

保存失败不转换成外部查询成功；失败记录本身也保存失败时，网页明确提示记录未保存。
此时当前响应显示本次失败，并将旧资料标为历史资料；刷新后只能读取此前已保存的查询结论，无法恢复未保存的失败记录。
已保存的配置和版本不会因查询失败或空结果被删除。新错误记录会遮盖配置中的 PAT、
常见 GitHub token 和 Bearer/token 凭据；旧错误记录不会被迁移重写，页面不展示原始异常。
明确分类已持久化，刷新和重启后按仓库展示最近结论、失败原因与环节。旧资料注明关联成功调用的取得时间，与 GitHub 发布时间分开；没有可靠关联时标为未知。最近失败或空结果不会删除旧资料，并明确它不代表本次查询成功。较新的未完成调用也不会沿用旧成功结论。

Release 资料保存仓库、GitHub Release 编号、标签、发布说明、来源链接、发布时间和
`prerelease` 类型。小写仓库名与 GitHub Release 编号识别同一 Release；重复查询
复用编号，更新类型以支持预发布转正式版，其他资料仍保留首次保存内容。
历史调用摘要保留当时查询到的类型，版本卡片展示最近一次查询保存的类型。

## 数据库

项目附带已建好表的 SQLite 数据库：

```text
src/diff_x_hunter/owner_repo/repository.db
```

数据库随源码和 Python 安装包交付，无需手动建表，也不在启动时自动迁移。程序直接使用包内的数据库文件；保存后退出程序，再运行 `list` 仍能读取配置。

当前工作区数据库已保留真实浏览器验收生成的 `psf/requests` 配置、版本资料和调用记录。

当前工作区旧库已先备份至 `.scratch/release-types/backups/repository.db`，
再为 `releases` 添加 `prerelease INTEGER NOT NULL DEFAULT 0`；旧记录按正式版保留，
原配置、资料编号和调用关联不变。其他旧数据库使用前先停止应用，再运行：

```bash
uv run python -m diff_x_hunter.migrate .scratch/release-types/backups/my-old-database.db
```

命令迁移应用使用的包内数据库，迁移前创建 SQLite 备份；备份路径必须不存在，
不会覆盖已有备份。已包含该字段的数据库再次执行不会变更。

`.scratch/release-query-failures/backups/before-query-outcomes.db`，并添加查询状态字段。

`watch_configs` 表包含两个文本字段：`repository`（仓库）和 `focus`（关注点）。

使用后，数据库文件会包含自己的关注配置。更新或重新安装前，请备份此文件并保留已有数据；对外分发时使用不含个人配置的空数据库。
